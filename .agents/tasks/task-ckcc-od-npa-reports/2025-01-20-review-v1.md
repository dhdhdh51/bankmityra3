# NPA KRM OTS report type, VisitFormData restructure, and HTML report generation

This change adds the CKCC NPA KRM OTS Scheme as a fourth report type to the field visit app, alongside a complete report generation and export pipeline. The form model (`VisitFormData`) is converted from a `data class` to a regular class to bypass the JVM 255-constructor-parameter limit the growing field set hit. A new `report` package introduces `ReportGenerator` (HTML), `ExcelExporter` (CSV), and `ReportViewActivity` (WebView + print/export). UI strings are updated to replace "BC Agent" with "BC Supervisor" and "BC code" with "BCBF Code".

Watch for: the deprecated `getSerializableExtra` in `ReportViewActivity` will fail on Android 13+ without the typed overload (confirmed); the "View Report" button from `VisitDetailActivity` is a placeholder toast, meaning the feature advertised in the menu doesn't function (confirmed); the NPA OTS section hardcodes KYC/Aadhaar/Mobile/Renewal fields to `false` in the PDF, hiding data the user's spec expects (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The JVM 255-parameter limit was hit because `VisitFormData` kept growing one field at a time. The fix moves all mutable fields out of the primary constructor into the class body, keeping only `val loanAccountId` as the constructor parameter. A hand-rolled `copy()` method supports the 22 fields that tests override. This works but introduces a maintenance trap: every new field must be manually added to `copy()` and `toFieldMap()` with no compiler enforcement.

The NPA OTS form section adds roughly 40 new fields mirroring the existing OTS section's structure: settlement amounts, deposit tracking, borrower response, recommendations, and status trackers. Validation follows the same pattern as the OTS section (percentage range checks, deposit traceability, validity window ordering). The serialization uses `npa_ots_details[field]` keys, consistent with the existing `ots_details[field]` and `ckcc_details[field]` namespaces.

The HTML report generator is a single-file string-builder that produces a self-contained A4 document with CSS print styling. It reads `VisitFormData` plus a `SupplementaryData` bag and emits all 9 visible report sections with XSS escaping and Indian currency formatting. The OTS section is conditionally included only for OTS and NPA OTS report types.

The report viewing pipeline passes HTML and a field map to `ReportViewActivity` via intent extras. Print and PDF both route through Android's `PrintManager` (same code path). Excel export writes a two-column CSV to the app cache and shares it via `FileProvider`. The field map travels as a `HashMap<String, String>` through the deprecated untyped `Serializable` extra API.

The `VisitDetailActivity` "View Report" menu item exists but does not produce a report; it shows a toast. This is dead UI shipped to production.

The user's spec includes these fields. Either add NPA OTS-specific collection fields or omit these rows from the NPA OTS report. (confirmed)
4. **`copy()` drift risk** — The hand-rolled `copy()` only copies fields explicitly listed in its body. New fields added to the class silently fail to propagate through `copy()`, making test assertions unreliable. Add a comment or test that asserts field count parity. (likely)

Two buttons with different labels doing the same thing confuses users. Either differentiate (direct-to-file PDF via `PdfDocument`) or merge into one button. (confirmed)

## VisitFormData restructure and the 255-parameter wall

Kotlin synthesizes `$default` constructors carrying additional bitmask parameters for each defaulted argument. At 308 fields, the synthetic constructor pushed well past 255. Moving all `var` fields to the class body eliminates constructor parameters entirely while preserving the same public API.

The manual `copy()` method covers 22 parameters that tests actually override. Every other field is copied by direct assignment inside the body. A new NPA OTS field added in the future that is not referenced by any test will silently vanish through `copy()`, making test assertions pass on stale data. Since `copy()` is only exercised from tests today, this is a test-correctness risk rather than a production bug, but it makes future test failures opaque.

## NPA OTS section: KYC fields rendered as hardcoded false

In `ReportGenerator.section4OtsDetails()`:

```kotlin
val kycComplete = if (isNpaOts) false else form.ckccKycComplete
val aadhaarSeeded = if (isNpaOts) false else form.ckccAadhaarSeeded
val mobileLinked = if (isNpaOts) false else form.ckccMobileLinked
val aadhaarAuth = if (isNpaOts) false else form.ckccAadhaarAuthCompleted
val willingToRenew = if (isNpaOts) false else form.ckccWillingToRenew
```

The user's PDF spec lists KYC Status, Aadhaar Seeded, Mobile Linked, Aadhaar Authentication, and Renewal Consent as part of Section 4. For NPA OTS reports these rows always display "No" / "Pending". If the NPA OTS form doesn't collect them separately, the report should omit the rows rather than print false negatives. If it should collect them, the `npaOts*` namespace needs new fields.

## Intent data transport for ReportViewActivity

```kotlin
@Suppress("UNCHECKED_CAST")
formFields = (intent.getSerializableExtra(EXTRA_FORM_FIELDS) as? HashMap<String, String>)
    ?: hashMapOf()
```

The `@Suppress("UNCHECKED_CAST")` hides the deprecation at compile time. On API 33+ the correct call is `intent.getSerializableExtra(EXTRA_FORM_FIELDS, HashMap::class.java)`. The data sizes here (HTML ~20KB, map ~10KB) are well within Binder limits, so this is an API-compatibility issue rather than a size issue. On devices running Android 14+ with strict mode, the deprecated path may log warnings or behave differently depending on OEM patches.

## VisitDetailActivity "View Report" is non-functional

The menu item `action_view_report` is inflated and handled with a toast. A field agent tapping it sees "View Report" text and nothing else. Either the menu item should be hidden until the report reconstruction is implemented, or removed entirely. Shipping dead UI in a compliance-oriented banking app creates confusion and support tickets.

## Print vs PDF button duplication

Both buttons in `ReportViewActivity` call:

```kotlin
binding.buttonPrint.setOnClickListener { printReport() }
binding.buttonPdf.setOnClickListener { printReport() }
```

Android's print dialog includes a "Save as PDF" option, so the user can reach PDF from the Print button. Having a separate "Save PDF" button that opens the same dialog sets an expectation of a direct file-save that isn't delivered. Either implement direct PDF generation (via `PdfDocument` or `WebView.createPrintDocumentAdapter` piped to a file) or consolidate into a single "Print / Save" button.

## Test coverage

Not tested: `ReportViewActivity` lifecycle and button handlers (requires Robolectric/Espresso), `PrintManager` integration, `FileProvider` URI resolution for CSV sharing, `VisitDetailActivity` menu handling.
